# GitHub Issueの作成

`Omluc/rakuriku-v2`の実装と既存Issueを根拠に、実装担当者が判断に迷わないIssueを作成する。

## 必須ルール

- GitHubの読み書きにはGitHubコネクタを優先して使用する。
- このSkillをIssue本文の唯一の文章規則として使用し、他のタスク・Issue作成Skillにある告知、テンプレート、出力規則を併用しない。
- 最初のIssue作成依頼は下書き作成の許可として扱い、GitHubへの書き込み承認とはみなさない。
- タイトル、Issue Type、親Issue、本文を含む下書きを提示し、その下書きに対する明示的な承認を得てから作成する。
- ユーザーが下書きを修正した場合は、修正版全体を再提示してから改めて承認を得る。
- リポジトリから確認できる事実をユーザーへ質問しない。探索しても決められない仕様・優先順位だけを確認する。
- 会話上の修正経緯やレビュー履歴ではなく、現在保証すべき仕様、責務、振る舞いを書く。
- ラベル、担当者、マイルストーンは、ユーザーが明示した場合だけ設定する。

## 実行フロー

### 1. 対象と接続を確認する

1. ローカルGitの`origin`を取得する。
2. `origin`が`github.com/Omluc/rakuriku-v2`を指すことを確認する。異なる場合は作成を止める。
3. `mcp__github__get_me`でGitHub接続を確認する。
4. `mcp__github__list_issue_types`で利用可能なIssue Typeを取得する。
5. `Bug`、`Feature`、`Refactoring`、`Chore`、`Research`のいずれかが不足している場合は、不足名を示して作成を止める。別のTypeへフォールバックしない。

### 2. リポジトリを調査する

1. 依頼の対象となる機能、現象、ドメイン用語、コード識別子を抽出する。
2. `rg`を使い、関連する実装、テスト、設定、ドキュメントを特定する。
3. 同じレイヤー、種類、ドメイン、パターンの既存実装を2〜3件読み、構造、命名、依存関係、エラー処理、テスト、import規約を確認する。
4. 現状の振る舞い、変更対象、影響範囲、既存のテスト方法を、確認できたコードに基づいて整理する。
5. 未確認のファイル、型、API、実装方式をIssueへ書かない。

### 3. 重複と関連Issueを調査する

1. `mcp__github__search_issues`で、目的、現象、ドメイン用語、主要なコード識別子を使って類似Issueを検索する。
2. 候補の本文を`mcp__github__issue_read`で確認する。
3. 同じ成果を求める未完了Issueがある場合は新規作成を止め、既存Issueを提示する。
4. 完了済みIssueと同じ現象や、重複か判断できない候補がある場合は、違いを示してユーザーへ確認する。
5. 明確に関連するIssueは本文で参照する。分割元が明確な場合だけ親Issue候補にする。
6. 親Issueは同じリポジトリに存在することを確認する。会話に出ただけのIssueを推測で親にしない。

### 4. Issue Typeを判定する

次の順序で最初に一致するTypeを選ぶ。

1. `Research`: 成果物が調査結果、検証結果、知見、意思決定である。
2. `Bug`: 既存の期待される動作と異なる問題を修正する。
3. `Feature`: 外部から観測できる機能や振る舞いを追加・拡張する。
4. `Refactoring`: 外部から観測できる振る舞いを維持して内部構造を改善する。
5. `Chore`: 依存関係、設定、CI/CD、運用、文書などを保守する。

判定結果を下書きに表示し、ユーザーが別のTypeへ変更できるようにする。

### 5. 下書きを作成する

タイトルは1行で、Issueが完了したときの成果または解消される問題を簡潔に表す。

本文には次の見出しをこの順序で使用する。

```md
## What（このタスクで実現すること）

## Why（このタスクを行う理由や経緯）

## How（どのように実装するのか）

## 完了条件

- [ ] 検証可能な完了条件
```

各セクションを次の責務に限定する。

- `What`: 実現する成果、対象範囲、必要なら対象外を記載する。実装手順を混ぜない。
- `Why`: コードや既存Issueから確認した現状、問題、必要性を記載する。実装方法を混ぜない。
- `How`: 既存パターンに沿った重要な実装方針、責務の移動、依存関係、検証方針を記載する。未確認の設計を断定しない。
- `完了条件`: 利用者の振る舞い、入出力、エラー、テストなど、完了を観測できる条件をすべて未チェックの`- [ ]`で記載する。

下書きは少なくとも次の形式で提示する。

```md
Repository: Omluc/rakuriku-v2
Issue Type: <判定したType>
Parent Issue: <#番号とタイトル、または「なし」>
Title: <タイトル>

<本文全体>
```

提示後に作成の承認を求め、承認されるまでGitHubへ書き込まない。

### 6. 承認後に作成する

1. 承認されたタイトル、本文、Issue Typeを`mcp__github__issue_write`の`create`で作成する。
2. 明示されたラベル、担当者、マイルストーンだけを作成時に設定する。
3. 親Issueがある場合は、作成結果が返したIssueのデータベースIDを使い、`mcp__github__sub_issue_write`の`add`で親へ紐付ける。Issue番号をデータベースIDとして渡さない。
4. 作成後のIssue URL、番号、Issue Type、親Issueを報告する。
5. Issue作成後に親子関係の設定だけが失敗した場合はIssueを削除せず、作成済みURLと失敗した操作を報告する。

## 品質チェック

下書きの提示前に次を確認する。

- タイトルだけで成果または問題が分かる。
- `What`、`Why`、`How`で同じ内容を繰り返していない。
- 実装担当者が会話ログを読まなくても理解できる。
- ファイルパスやコード識別子はリポジトリで存在を確認している。
- 完了条件がすべて`- [ ]`で、判定可能な表現になっている。
- 重複Issueの検索結果を確認している。
- Issue Typeと親Issueを下書きに表示している。
- GitHubへの書き込み前に、提示した下書きへの明示的な承認を得ている。
