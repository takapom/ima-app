固定の指示と、毎回変わるデータを分ける

MODEL_SYSTEM_PROMPTに判断方針を固定し、原文と文脈はima_turn_contextのJSONとしてuser messageへ渡す。店舗情報や過去発言をsystem instructionへ連結しない。 

[
  { role: "system", content: MODEL_SYSTEM_PROMPT },
  { role: "user", content: JSON.stringify({
      kind: "ima_turn_context",
      originalUserText: "恵比寿のカフェを探して",
      context: { /* 条件・履歴・候補・根拠・機能・予算 */ }
  }) }
]

encodeModelContext()の構造を短縮した説明用コード。

モデルが受け取るもの

原文、地域表現、今回の条件、履歴と抜粋、表示中カード、却下候補、許可された根拠、利用可能機能、残り予算。

サーバー内に留めるもの

認証由来のowner情報、秘密鍵、DB handle、生の位置座標、Providerの生レスポンス。位置は状態と地域説明へ投影する。

設計方針意図理解、検索語への変換、追加質問、候補選定はモデルが担当する。固定の意図分類器や全入力に共通の探索順は置かない。「質問は原則1つ」「前の要望を引き継ぐ」「不適合店で候補数を埋めない」とプロンプトとTool説明で指示する。

設計の読み取りモデルに判断材料を渡しつつ、所有者や保存状態を直接操作させない構成。データと指示の分離に加え、Tool・根拠・確定を実行時に検証する。prompt injectionを完全に防ぐ保証を示すものではない。

根拠：AIの振る舞い / system prompt / 文脈JSONの組み立て / モデル文脈への投影

4. 3つのToolと、2つの終端

Tool モデルが決めること アプリの担当
search_places 地域、短い検索語、再検索・継続、除外候補。 入力・scope・cursorを検証。Providerへ問い合わせ、候補を登録。
get_place_details 候補の配列、必要なfield。 登録候補と対応fieldを検証。詳細を観測ID・出典・期限付きで返す。
submit_cards 主提案1件、別案0〜2件、理由、別案との差、根拠ID。 候補・根拠・条件を検証し、完成カードを1回確定。

Tool引数は{ input: {...}, metadata: {} }。metadata.turnConstraintsに今回の条件変更案を載せる。4つ目のToolや保存設定の更新操作にはしない。

cards / replace

submit_cardsが成功するとカードを置き換える。messageは1〜4件・各300字以内、whyは80字以内、別案のdiffは40字以内。候補の重複と0件カードは許さない。

message / keep

Toolなしのstepでfinal_messageのJSONを返す。300字以内のメッセージ1件。質問・説明・比較に使い、既存カードを維持する。 

{
  "kind": "final_message",
  "message": {
    "text": "どのあたりで探しますか？",
    "evidenceIds": [],
    "basis": "conversational"
  },
  "metadata": {}
}

理由文にはgrounded（根拠付き）、inference（推測）、conversational（会話上の発言）の区分を持たせる。heroは内部の第1候補名で、現行UIは最大3件を同じ大きさ・同じ操作で並べる。

根拠：3つのTool定義 / 候補選択と応答schema / 製品仕様 / HTTPと応答契約
