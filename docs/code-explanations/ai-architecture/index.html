AIが探索を進め、

ima. のAIは、自由記述と会話の文脈から「何を調べ、どの店を提案するか」を判断する。検索結果の管理、根拠の検証、条件の適用、保存、画面への配送はWorker側が担当する。

2. 「恵比寿のカフェを探して」の実行順

コードから組み立てた代表例。実行ログではなく、Toolの選択順や呼び出し回数はモデルと取得結果によって変わる。

  1. 発話を先に保存する

    MobileがPOST /v1/conversations/:conversationId/turnsへ送信。会話DOが発言とrunを受理し、202を返す。端末は同じrunのイベントを購読する。

  2. 実行単位と会話の文脈を用意する

    ConversationExecution.execute()がThreadを選び、受理した発話より前の履歴を読む。Threadが失効していれば新しく作り、旧候補IDは持ち越さない。

  3. AIに見せる入力を投影する

    projectModelContext()が原文、地域、条件、履歴、表示中カード、根拠、使える機能、残り予算を整える。各stepで時刻と保持条件を再評価する。

  4. モデルが検索を選ぶ

    search_placesを呼び、地域とジャンル語をHot Pepperへ渡す。取得した店舗はRegistryへ登録し、内部の候補IDをモデルへ返す。

  5. 候補の詳細をまとめて取得する

    get_place_detailsへ候補の配列とfieldを渡す。identity、掲載営業時間、必要に応じて価格・写真・設備を、観測ID付きで受け取る。

  6. 選定理由を提出し、アプリが検証・確定する

    submit_cardsへ候補ID、観測ID、理由文を提出する。Coreが検証し、CommitPortがrevisionを確認して1回確定する。committedでループを止め、成功後の追加生成は要求しない。

  7. 履歴へ配送し、完成カードを表示する

    会話履歴への配送は冪等。SSEでは状態と完成DTOを渡し、文字単位の生成配信は行わない。

質問だけで終わる経路もある。地域が不明なら「どのあたりで探しますか？」をfinal_messageで返せる。既存候補への説明・比較もメッセージで答え、現在のカードを維持する。

根拠：HTTPと応答契約 / 会話とThreadの実行連携 / モデル文脈への投影 / 3つのTool定義 / 応答の確定Application

モデルが受け取るもの

原文、地域表現、今回の条件、履歴と抜粋、表示中カード、却下候補、許可された根拠、利用可能機能、残り予算。

サーバー内に留めるもの

認証由来のowner情報、秘密鍵、DB handle、生の位置座標、Providerの生レスポンス。位置は状態と地域説明へ投影する。

設計方針意図理解、検索語への変換、追加質問、候補選定はモデルが担当する。固定の意図分類器や全入力に共通の探索順は置かない。「質問は原則1つ」「前の要望を引き継ぐ」「不適合店で候補数を埋めない」とプロンプトとTool説明で指示する。

設計の読み取りモデルに判断材料を渡しつつ、所有者や保存状態を直接操作させない構成。データと指示の分離に加え、Tool・根拠・確定を実行時に検証する。prompt injectionを完全に防ぐ保証を示すものではない。

根拠：AIの振る舞い / system prompt / 文脈JSONの組み立て / モデル文脈への投影

4. 3つのToolと、2つの終端

Tool モデルが決めること アプリの担当
search_places 地域、短い検索語、再検索・継続、除外候補。 入力・scope・cursorを検証。Providerへ問い合わせ、候補を登録。
get_place_details 候補の配列、必要なfield。 登録候補と対応fieldを検証。詳細を観測ID・出典・期限付きで返す。
submit_cards 主提案1件、別案0〜2件、理由、別案との差、根拠ID。 候補・根拠・条件を検証し、完成カードを1回確定。

Tool引数は{ input: {...}, metadata: {} }。metadata.turnConstraintsに今回の条件変更案を載せる。4つ目のToolや保存設定の更新操作にはしない。

cards / replace

submit_cardsが成功するとカードを置き換える。messageは1〜4件・各300字以内、whyは80字以内、別案のdiffは40字以内。候補の重複と0件カードは許さない。

message / keep

Toolなしのstepでfinal_messageのJSONを返す。300字以内のメッセージ1件。質問・説明・比較に使い、既存カードを維持する。 

{
  "kind": "final_message",
  "message": {
    "text": "どのあたりで探しますか？",
    "evidenceIds": [],
    "basis": "conversational"
  },
  "metadata": {}
}

理由文にはgrounded（根拠付き）、inference（推測）、conversational（会話上の発言）の区分を持たせる。heroは内部の第1候補名で、現行UIは最大3件を同じ大きさ・同じ操作で並べる。

根拠：3つのTool定義 / 候補選択と応答schema / 製品仕様 / HTTPと応答契約

5. 根拠を検証してから、1回だけ確定する

Providerの結果は候補と観測に分ける。候補IDは「どの店か」、観測IDは「その店のどの情報を、いつ・どの条件で取得したか」を指す。

検査 確定前に確認すること
候補の所属 現在のowner・threadに登録済みか。却下済みや重複ではないか。
根拠の対応 観測IDが存在し、その候補・fieldに結び付くか。出典と値がschemaを満たすか。
鮮度と文脈 現在の条件・位置revisionと一致するか。期限切れや新しい観測との矛盾がないか。
カードの必須情報 identityとopening_hoursの根拠があるか。明示された閉業状態や必須条件に違反しないか。
確定の競合 現在のrevision・実行状態と一致するか。同じ冪等キーに異なる内容が紐づいていないか。

LLMが提出する中心はIDと理由文。店名・住所・営業時間などのカード本体は、検証済みObservationから取り出す。価格・写真・設備は、LLMが引用し忘れてもApplicationが有効な観測を補完する。出典もObservationから組み立てる。

ThreadDOのSQL transactionでrevision更新、確定記録、run完了、会話への未配送記録を扱う。同一内容の再送は同じ確定結果を使い、古い実行からの上書きを防ぐ。

根拠：カード確定前の検証 / 表示用情報の補完 / 根拠の鮮度・所属の検証 / 応答の確定Application / SQL・CAS・冪等確定

自然文の正しさまで自動証明する仕組みではない。resolveEvidenceText()は引用IDと利用可能性を検証するが、理由文の意味が根拠と一致するかまでは判定しない。「カフェ」という情報だけで「静か」と言うような飛躍は、プロンプト・評価・レビューで扱う。

条件変更には元発話IDと原文の完全一致部分文字列のquoteが必要。ただしquoteから変更値が意味的に導けることを証明する仕組みではない。検証した変更は今回の条件にだけ適用し、保存済みprefsは直接書き換えない。

根拠：理由文の検証範囲 / 条件変更と原文の検証 / モデル評価の定義とテスト

6. 自律探索を制限する実行制御

wrapRuntimeModelGuard()がモデルのstep全体をバッファし、SDKがToolを実行する前に検査する。同じstepの読み取り＋確定、複数確定、未知のToolを拒否する。読み取りだけの複数操作は表現できる。

Toolと同時に出る「探します」などの前置きは、ユーザー向け終端に採用しない。Toolなしのstepだけがメッセージ終端になり、最終応答用stepではToolを無効にする。空の終端や不正なenvelopeは確定なしとして扱い、提案成功へ変換しない。

既定の上限 値 目的
turn全体 / 最終応答の予約 60秒 / 10秒 状況を返す余地を残す。
モデル呼び出し 最大6 step 無制限の探索ループを防ぐ。
読み取り / 同時読み取り 最大8回 / 2件 Toolの負荷を制御する。
Provider HTTP 最大20 request Tool内部の外部問い合わせも数える。
確定の修正 / 読み取りretry 最大2回 / 1回 修正可能なinvalidを返す。SDKの自動retryは0。
検索 / 詳細timeout 3秒 / 4秒 Provider読み取りを時間制限する。

実測latencyや料金ではなく、コードの既定上限。costUnitsも内部予算単位であり、通貨額ではない。

キャンセル・古いrevision・確定済み状態も実行境界で止める。liveの設定不足やAPI障害をfixtureへの暗黙切り替えで隠さない。

根拠：モデル出力の実行前検査 / 操作の組み合わせ検査 / 実行予算の既定値 / 最終応答stepの制御 / 実モデル・実店舗APIの起動手順

7. 会話の記憶、今夜の根拠、保存する参照

データの正 保持するもの AIとの関係
ConversationHistoryDO 会話・発言・run。ユーザー原文は削除まで、回答は保持条件付き。 履歴・抜粋をモデルへ投影。過去の文を最新店舗情報の根拠へ昇格させない。
ThreadDO 今夜の実行状態、候補・観測の文脈、確定参照。 期限付きの探索単位。失効後は同じ会話へ新Threadを結び付ける。
SavedReferenceDO 保存prefs、店舗identityの参照、決定時刻。 保存レコードに店名・写真・理由本文を埋め込まない。
端末SQLite 会話・保存一覧の投影とキャッシュ。 サーバーが正。独立したAIの記憶ストアではない。

現在の「要約」はユーザー原文の抜粋

SqlConversationMemoryは直近最大32メッセージから、1件最大500文字・合計8,000 bytesの履歴を作る。それより古いユーザー発言の先頭4件と末尾4件を対象に、各160文字・合計4,000 bytes以内で抜粋する。元メッセージID、sequence、extractive_v1を持つ。

含意LLMによる意味要約や全会話検索ではないため、長い会話の途中にだけ出た条件が入力から抜ける可能性がある。現在の原文と明示的な条件を優先し、不足があれば確認する設計。

鮮度と保存期限は別に扱う

Hot Pepper由来の観測は鮮度30分。表示・保持の上限はThread作成時に確定するJST 05:00のsession期限で、再取得や再起動で延長しない。生成文も引用元の保持条件を継承する。

SDK保存前と再利用前にpolicyと期限を検査し、保存禁止・由来不明の本文は参照用の表現へ置換する。当該turnのTool結果と永続履歴を分け、由来不明のSDK compaction summaryも復元しない。写真URL・帰属などは扱うが、画像bytesはモデルに渡さない。

通信断後は同じrunを再照会する。確定結果は会話履歴へ冪等配送し、生成をやり直して回答を増やさない。期限切れや再起動後の復元は、許可された本文と参照の範囲に限られる。

根拠：アーキテクチャ / 履歴と抜粋要約 / 会話とThreadの実行連携 / SDK保存前の制御 / 鮮度30分と保持期限 / データ利用・保持方針 / HTTPと応答契約

8. 現在の機能と制約

型やテストに存在する機能と、現在のProvider構成で接続している機能は区別する。ここでは現行compositionを基準にする。

項目 現行の扱い
店舗検索・詳細 Hot Pepper。地域名はkeyword、現在地は緯度経度とrangeで検索。keywordは空白区切りのAND検索で、モデルの検索語の選び方が結果に影響する。
営業時間 掲載文を返し、営業中・到着時営業・ラストオーダーは推定しない。allowUnknownOpening:trueにより、営業未確認でも候補提示を許す。
価格・設備・写真 取得内容を表示。予算文から価格単位や数値範囲を補完せず、写真URLから雰囲気を推測しない。
徒歩経路・終電 capabilitiesは両方false。端末の条件入力から外し、モデルが提案した徒歩上限・帰宅駅も採用しない。掲載アクセス文は経路の計測根拠にならない。
最低滞在時間 必須条件として残す。実装は徒歩の到着根拠と営業時間を要求するため、現在のProvider構成でこの条件が有効ならカードを確定できない。営業未確認の許容では解除されない。
保存店舗の再取得 API・契約の形はあるが、保存一覧のrefreshと別Threadへの読み込みは現在未提供。

根拠：現在の接続機能 / 3つのTool定義 / 店舗データの観測への変換 / 営業未確認を許容する設定 / 最低滞在と帰宅条件の検証 / 未対応条件の採用抑止 / データ利用・保持方針

submit_cardsのdescriptionには「引用しなかったfieldはカードに表示されません」とある。一方、現行のattachDisplayObservations()は価格・写真・設備を補完する。本資料は実際のコードの動作を説明している。説明文の整合は修正候補であり、今回コードは変更していない。

根拠：3つのTool定義 / 表示用情報の補完

9. 評価の仕組みと、今回の確認範囲

Coreの単体テストで根拠・条件・確定を扱い、実SDK/DOと固定モデル・固定Providerの統合テストで実行・保持・再送の境界を検証する。モデル評価には新規検索、条件変更、説明、比較、候補失敗、prompt injection、会話継続、repairなど14シナリオ×3反復の定義がある。

実モデル評価runnerは実OpenAIモデル＋固定Providerを使う別ゲート。実店舗APIの接続確認とは区別する。人手レビューのcoverageと重大違反も判定へ含め、未測定コストを0として扱わない。

モデル・Provider・turnのtraceを持ち、モデル呼び出しではstatus、resultCode、duration、tokenCountなどの構造化項目を計測する。本文・秘密・生座標をテレメトリへ記録しない方針。

今回未確認テストの現在の合否、実モデルの品質、実APIの成功、実機、稼働環境のlatency・料金・配布状態は測定していない。既存テストの存在と判定内容を読解した段階であり、合格を報告する資料ではない。

Providerポリシーでは、取得内容の外部LLM送信に関する明示的許諾と個別アカウント条件も未確定と記載されている。アプリのallow設定はProvider側の検収済みを意味しない。

根拠：モデル評価の定義とテスト / 実モデル評価の対象 / モデル呼び出しの計測 / データ利用・保持方針
