# ADR 0003: ツールはプラグイン、提案のあとに対話する

- **Status:** Accepted
- **Superseded in part by:** [0009](./0009-contextual-response-presentation.md)（メッセージ併用・質問に応じた提示。本文の候補UIのみという制約は履歴）
- **Date:** 2026-09-07
- **Deciders:** プロダクトオーナー（本議論）
- **Tags:** product, agent, ux
- **Supersedes (in part):** [0001](./0001-in-the-moment-next-spot.md) §4.2「話し相手ではない」、§4.1「3往復しないと候補が出ない」の読み（最初の3件は維持。その後の往復は対話）

0001 の骨格は維持する。

```
自由記述 → 提案UI（主1+別2）→ ここにする → 地図 / LINE
```

覆すのは「エージェントは一発で終わって沈黙する」ことと、「ツールは固定パイプライン」ことである。

---

## 1. Context

0001 は、歩道で ChatGPT のように長文で話し続けると負ける、としてエージェントを「話し相手ではない」と切った。ツールは今行ける3件を出す手順の一部だった。

その後の修正:

- ツールは手足であるだけでなく、**プラグイン**である。エージェントの選択肢を広げる。固定の店検索パイプラインに閉じない
- ユーザーは自由記入し、AI が提案 UI を出す。そのあと **フィードバックや追記プロンプト** で、求めているものへ寄せる。対話を可能にする

0001 が守るべきなのは「最初の3件の前に5回聞き返さない」ことである。最初の提案のあとの対話まで禁じたのは、広すぎた。

---

## 2. Decision

### 2.1 ツールはプラグインである

**Decision:** ツールはハーネスに登録するプラグインである。エージェントはカタログからアクションを選ぶ。新しい能力はプラグインを足して増やす。ハーネス本体を書き直してパイプラインを伸ばさない。

プラグインの契約:

- 名前、いつ使うかの短い説明（エージェントが選ぶため）
- valibot の入力と出力
- 実行はハーネス（キーも HTTP もプラグイン側。モデルは触らない）
- 失敗は結果として返す。発明しない

NVP で入っているプラグイン:

- 店を探す（Places）
- 営業を見る
- 徒歩を見る
- 終電を見る
- 保存を見る
- ホットペッパー上乗せ（任意）
- 提案を出す（`submit_cards`）

後から足してよい例（今は実装しない）: 天気、空席、別エリア。足すまでエージェントはそれを選べない。無いプラグインの結果を捏造しない。

プラグインは「必須手順の関数」ではない。**選択肢を増やすもの**である。ただし `submit_cards` は、出した id がこの run で観測済みで、営業・徒歩・終電のプラグイン結果と矛盾しないこと、をハーネスが拒む。選択肢が広いことと、嘘を出せることは別である。

### 2.2 最初の提案は聞き返しなし。そのあとは対話してよい

**Decision:** 1通目で提案 UI（主1+別2、または正直な欠件）を出す。診断や5問はしない。提案のあと、同じ欄への追記・`ちがう`・チップは **対話のターン** である。エージェントは直前の提案とユーザーのフィードバックを見て、プラグインを再使用し、提案 UI を更新する。

流れ:

```
空キャンバス
  → 自由記述 1通目
  → 提案 UI（90秒ジョブはここで完了してよい）
  → 追記 / ちがう / 「もっと静か」     ← 対話
  → 更新された提案 UI
  → ここにする → 地図 / LINE
```

対話でやってよい:

- 条件を足す・外す（甘いのやめた、もっと近い）
- 今の主提案を却下して寄せる
- 直前の3件を文脈に残す

対話でやってはいけない:

- 最初の3件の前に聞き返す
- デートプランを語る長文
- 提案 UI をやめてチャット履歴を商品にする
- 何往復してもカードを出さない

成功の主指標は変わらない。探す役が90秒で最初の3件を出せたか。対話は、3件が「まだ違う」ときの寄せであり、必須ではない。

### 2.3 セッションは今夜の一文ではなく、提案スレッドである

**Decision:** サイドバーの「今夜の検索」1行は、空キャンバスからの1スレッドである。スレッドの中に複数ターンがある。`新しい検索` でスレッドを閉じる。

モックの「バブルは常に1つで置換」は、1通目の単純化だった。対話を入れるなら、ユーザー発話は積む。アシスタントの本文は積まない。積むのは **提案 UI の更新** である。

## 3. 0001 から読み替えるもの

| 0001 | 0003 |
|---|---|
| エージェントは話し相手ではない | 最初の提案の前は聞き返さない。提案のあとは対話して寄せる |
| 3往復しないと候補が出ない、は不採用 | **最初の候補が3往復待ち**は不採用のまま。候補の**あと**の往復は採用 |
| 同じ欄で条件を足す | 同じ。それは対話の入力である |
| チャット履歴が商品そのもの、は不採用 | 維持。商品は提案 UI。履歴は探す役のメモ |
| ツールは探索手順 | ツールはプラグイン。手順ではなく選択肢 |

NVP の核は残す:

> 自由記述1回から「今行ける」最大3件が出る。90秒以内に次へ進めてよい。足りなければ、同じ画面で対話して寄せる。

---

## 4. Consequences

良い結果:

- 「まだ違う」を新しい検索にせず、探す役の負荷を軽くしたまま寄せられる
- 能力追加がプラグインになり、予約や天気を本体に溶かしにくい
- ChatGPT の心的モデル（書いて、返って、書き足す）と、カードという商品が共存する

悪い結果・負債:

- 対話を長くすると歩道の90秒が死ぬ。最初の3件の品質が本体のまま
- プラグインを足すほど、モデルが関係ない手を使う。カタログは短く、説明は「いつ使うか」だけ
- セッションが伸びると SearchAgent を oneshot で捨てられない（設計の DO 寿命をスレッド単位にする）
- 提案が会話のたびに全部入れ替わると、相手に見せた店が消える。更新は主提案の差し替えを基本にし、ユーザーが残した店は消さない

## 5. 未決

- 対話ターンの提案を、同じカード枠を更新するか、下に新しいブロックを積むか（初期は **枠を更新**。ユーザーバブルだけ積む）
- プラグインの発見をモデルに全部任せるか、NVP は店・営業・徒歩・終電を「よく使う手」として説明に書くか（初期は後者。カタログは全部渡す）
- 何ターンで「新しい検索した方がいい」と出すか（初期は出さない。ユーザーが ＋ する）
