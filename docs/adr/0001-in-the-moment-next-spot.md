- **Deciders:** プロダクトオーナー（本議論）

## 1. Context

デート中に「これからどこ行く？」が発生する。計画はすでに終わっているか、最初の店が終わった直後である。残っているのは時間・体力・金・終電と、どちらも先に欲しいと言えない真空である。

既存の回避策:

- Google マップの「営業中」
- Instagram
- 食べログ / ホットペッパー
- ChatGPT への雑な質問（営業・待ち・距離が保証されない）
- いつものカラオケ / カフェ
- 片方が決める
- 歩く
- 帰宅

狙いは、デート前日のプランナーではない。緊急で次のスポットを決めることである。ターゲットはまずカップル、将来は友達・知り合い・同僚へ同じジョブで広げる。UI の骨格は ChatGPT のような自由記述である、という希望が出発点だった。

類似はすでに存在する（「今日、なにする？」、Hangry Helper、Nibbl、WhereNxt、トレタnow、ホットペッパー席押さえ など）。差は機能の多さではなく、**予定崩壊後の90秒**に特化できるかどうか、という仮説で進めた。

---

## 2. Decision (要約)

**書いて送ると、エージェントが「今から行ける」店・スポットを最大3件出し、主提案1 + 別案2で決める。サイドバーは今夜の検索履歴。外部連携の最初は、決めた店を LINE で送ること。**

これを NVP（最初に検証する価値）とし、それ以外は深く広げない。

採択した骨格:

```
自由記述 → エージェント探索 → 主提案1 + 別案2 → ここにする → 地図 / LINE
```

---

## 3. ジョブと NVP

### 3.1 片付けるジョブ

雇われる理由は店探しではない。

> すでに外出していて、今の予定が終わり、残り時間・体力・金・終電がある。どちらも「なんでもいい」と言う。その真空を、相手を責めず、空気を壊さず、今から実際に行ける次の場所へ変換する。

短くすると、**「次どこ行く？」を関係のテストから、残時間の運用問題に変える。**

状況つきジョブ文:

> When 最初の食事や予定が終わり、歩道や店の前で「次どこ行く？」が出て、残り1〜3時間あるが候補が頭にない  
> I want to 今の気分と制約に合う、実際に入れる場所へすぐ動く  
> so I can 今夜を「楽しかった」で閉じ、どちらか一方が決断の責任を全部背負わずに済る

成功指標:

- 決定までの時間（目標: 90秒以内）
- 実際にその場へ移動したか
- 到着して入れたか
- 残時間を使い切れたか
- どちらも「自分が我慢した」と感じなかったか
- スマホを見ていた時間が、デートの空気を殺さなかったか

### 3.2 NVP

検証する価値は次に固定する。

> 都心の夜、食事の直後、終電制約がある状態で、自由記述1回から「今行ける」最大3件が出て、90秒以内に次の店へ歩ける。

これは十分強いので、関係深化・日記・全国・多連携・多機能サイドバーは、NVP が歩道で雇われるまで後回しにする。

### 3.3 進化の妨げとして取り除くもの

セッション層:

- 決定の真空（なんでもいいの応酬）
- 探索そのものが空気を殺す（長いチャット）
- 実行可能性の不確実性（開いてる？ 待たされる？ 終電？）
- ハズレの責任が片方に寄る
- 迷うほど候補が減る時間減衰

関係層（副産物。目的にしない）:

- プランナー負担の固定化
- 選好の不可視化
- 同じ店ループ

取り除くのは「情報不足」ではなく、**ハズレを引く恐怖と、探索に時間を使うこと自体**である。

### 3.4 ポジション

デート当日の流れ:

`信号（今の予定が終わる）→ 意思決定（次どこ）→ 準備（移動・待ち）→ 行動 → 検証（入れた？）→ 例外（満席）→ 記録`

入る位置は **意思決定 + 今行けるかの検証**。発見（Instagram）でも、記録（アルバム）でも、予約プラットフォームそのものでもない。

ポジション文:

> 都市部で外出中のカップルが、最初の予定の直後に「次どこ行く？」で止まった時、私たちは今から行ける次の一手の意思決定と実行可能性の検証になり、Googleマップや口頭の譲り合いより、残時間内に実際に入れる場所へ90秒で着地させる。利用ごとの「行った / 入れた / 合った」によって、同じ状況の次の提案が速くなる。

### 3.5 Need の扱い

汎用の「カップルの行き先決め」は Nice-to-have に寄りやすい。Need が立つ交差点は、終電・貴重な残時間・満席や雨などの予定崩壊・土地勘のなさ、が重なった時だけである。最初の楔は **終電がある都市の夜** に固定する。

友達・同僚への拡張は、日記機能ではなく **人数と幹事負担（二次会）** で行う。ジョブの核は `少人数 × 現在地 × 残時間 × 制約 → 今行く一手`。

## 4. 詳細決定

### 4.1 入力は ChatGPT LIKE の自由記述

**Decision:** 入口はフィルターでもスワイプでもなく、一文で状況を書ける画面。

理由:

- 状況が毎回違う（疲れた、甘い、終電、雨）
- フォームだと本当に言いたいことが切れる
- ChatGPT が強いのは精度ではなく、形式を考えずに投げられること

入力の契約:

- 開くと入力欄が一つ
- プレースホルダは「いま何してる？そのまま書いて」
- 例文はヒントであり必須ではない
- 書いた言葉が最初のメッセージになる
- 条件の追加も同じ欄に書く
- 検索語の候補は、入力欄の上に短い語として出す（文章例ではない）

検索語候補の出し方:

1. 入力前: 終電・徒歩・予算、気分、よく使う条件
2. 入力中: 今の語に前方一致・部分一致（`終` → `終電 渋谷`）
3. 文があるとき: `+ 静か` のように後ろに足す
4. タップは入力に足すだけ。検索は ↑ で送る

採用するもの / しないもの:

| 採用 | 不採用 |
|---|---|
| 空キャンバスと下の自由入力 | アシスタントが店を長文で語る |
| 口語・途中の文 | ジャンル選択や診断 |
| 同じ欄で条件を足す | 3往復しないと候補が出ない |
| 左に今夜の履歴 | チャット履歴が商品そのもの |

### 4.2 エージェントは雑談せず、今行ける3件を返す

**Decision:** 検索後、エージェントが店舗・スポットを提案する。話し相手ではない。

手順:

1. 状況を読む（自由記述 + 現在地・時刻 + 保存した条件）
2. 近くで今開いている店とスポットを見る
3. 歩ける距離と終電で落とす
4. 主提案1と、理由の違う別案2を返す

返すのは文章ではなくカード用データ（名前、写真群、徒歩、営業、理由1行、差）。店に限らず、残時間と気分が合えばスポットも含む。

やってはいけない:

- デートプランを語る
- 5回聞き返してから出す
- マップ一覧の貼り付け
- 閉店・遠すぎ・終電不可を「おすすめ」にする

閉店・満席・終電ミスはエージェントの失敗である。

### 4.3 結果UI: 主提案1 + 別案2

**Decision:** 結果は検索ヒット一覧ではない。1件を決めて、2件を見比べる。

- 主提案: 写真（複数枚を写真枠だけ横スクロール）、店名と徒歩は写真の上に固定、理由は最大2行、操作は `ここにする` / `ちがう`
- 別案: 行。差（より静か / もっと近い）と分数と予算。行のテキスト側をタップすると主提案と入れ替わる。サムネ写真枠も横スクロール可
- `残す` は緊急操作から外し、写真上の小さなボタン
- チップは最大4。終電の二重表示はしない
- 決めたあと: `地図を開く` / `LINEで送る`

写真スクロールはカード全体ではなく **写真領域だけ**。店の入れ替えと混同しない。

却下した結果UI:

- 3件同じ大きさ（また「どれがいい？」が始まる）
- Tinder スワイプ（歩道では遅い）
- 別案を小さいカード2枚（本文が読めず、比較軸が埋まる）

### 4.4 サイドバーは ChatGPT の履歴

**Decision:** サイドバーの本体は今夜の検索履歴である。機能名を並べない。機能は2つまで。

```
新しい検索
────────────────
恵比寿 · 食後    21:14
雨 · 二軒目      20:06
────────────────
条件
保存
```

| 置くもの | 役割 | 機能として数えるか |
|---|---|---|
| 新しい検索 | 空の入力に戻る | 数えない。入口 |
| 今夜の検索一覧 | さっきの一文に戻る | 数えない。履歴 |
| **条件** | 終電・徒歩・予算 | 機能 1 |
| **保存** | 行った / また行きたい / 行かない | 機能 2 |

`保存` の中に3状態をまとめる。名前を3機能にしない。

サイドバーから外したもの:

- 気分から → 入力候補で足りる
- よく使う条件 → 同上
- 今夜を共有 → 履歴や決定後の操作。機能名にしない
- アルバム、記念日、診断、デートコース

電話ではハンバーガーの奥。緊急中は開かなくてよい。机では左カラム常時。

### 4.5 最初の外部連携は LINE

**Decision:** 他ツールを同時に足さない。最初は LINE。置く場所はサイドバーではなく、**店が決まった直後**。

流れ:

1. 候補を見る
2. ここにする
3. 地図を開く / LINEで送る

送るもの: 店名、徒歩、地図リンク。相手がアプリを持っていなくてよい。

最初にやらない LINE:

- サイドバーに「LINE連携」という項目
- LINE ログイン必須（歩道の摩擦）
- 「今夜どう？」通知（計画アプリ化）
- マップ・Instagram・カレンダーとの同時連携

将来ありうるが NVP 後: LINE 公式に書いて候補が返る、LIFF でインストールなし。探す本体を LINE に移すのは、また別アプリを開く話になるので後回し。

### 4.6 見た目

**Decision:** Z世代向け。最初の「夜の店メニュー」（茶色・明朝・静かな高級感）は却下。蛍光ライム全面塗りも却下。

採択:

- 地: ほぼ黒
- アクセント: 落ち着いたライムを点だけ（ロゴの点、NOW、別案の差）
- 主ボタン: オフホワイト
- 見出し: Dela Gothic One、本文 Noto Sans JP
- 仮称: ima.

コピーは口語。「行く」ではなく状況に応じて `ここにする`。

### 4.7 供給と最初の市場

**Decision:** 最初は店密度と終電がある都市の夜（東京など特定エリア）。全国同時は品質事故になる。

エージェントが保証すべき最低の真実: 今開いている、今から届く、満腹/飲酒/体力と矛盾しない、予算感が外れていない。

複利の主ループ（仮説）:

`その場で決めて行った → 状況×結果のラベルが残る → 同じエリア・時間帯の次回が速くなる → また開かれる`

「データが増えるとAIが賢くなる」だけでは複利と呼ばない。

## 5. 却下した道

| 候補 | 却下理由 |
|---|---|
| デートプランナー | 本業が緊急ではない。マップ・Instagram と正面衝突 |
| カップルOS（カレンダー、アルバム、記念日） | Between / Coupply の棚。歩道で開かれない |
| ChatGPT の皮を被せた Places API | 入力は会話、出力も長文、だと歩道で負ける |
| スワイプで二人の好み合わせ | 時間がある時のジョブ。緊急では遅い |
| 機能名が8つ並ぶサイドバー | 機能が多いアプリに見える。must は少数 |
| 最初から友達・同僚向け | 物語はカップル、Need は二次会が強いが、NVP はカップルの夜で取る |
| 多連携同時 | 探す本体がぼやける。LINE の「決めた店を送る」が先 |

## 6. Consequences

### 良い結果

- 何のアプリか、開いた瞬間に分かる（書いて送る）
- 90秒ジョブと UI が一致する（チャットを続けない）
- サイドバーが ChatGPT と同じ心的モデルなので説明コストが低い
- LINE が「決めたあと」にあるので、インストールしていない相手にも渡せる
- 機能が増えにくい。足したくなるものは履歴・条件・保存のどれかに入るか、入らない

### 悪い結果・負債

- 今行ける保証（営業・待ち・終電）の供給が本体コスト。UI では解けない
- 歩道で新規アプリを開く摩擦は残る。LINE 送付は決定後の話で、探索そのものの起動は未解決
- Google マップ + Gemini が同じジョブを取るリスクは残る
- 利用頻度が低い（デートは週次以下）ので、想起されないリスクは残る
- 「行った / 入れた / よかった」が溜まるまで、提案は汎用に見える
- 都心以外ではスカスカになりうる

### リリース後に失敗しやすい形（この決定を前提にした）

1. その場で開かれず、マップか帰宅で済む
2. 閉店・待ち・終電ミスを1回出して解雇される
3. Google が会話×近くを取る
4. 使わず忘れられる
5. 払われない（店探し無料がデフォルト）
6. スマホを出すこと自体が空気を壊す
7. 都心の夜以外でヒットしない
8. カップルでは Need が弱く、二次会に行く前に終わる
9. 結果ラベルが残らず ChatGPT ラッパーに見える
10. サイドバーに機能を足して緊急ツールでなくなる

本体の成功指標はダウンロード数ではない。**困ったその夜に開いて、実際にその店へ歩いたか。**

## 7. 実装上の現状

- この決定時点の UI スナップショット: [0001-ui.html](./0001-ui.html)（当時の HTML をそのまま添付）
- 作業用モック: `next-spot-mockup/index.html`
- ローカル確認: リポジトリ内の静的 HTML。検索語候補、結果カード、写真スクロール、履歴サイドバー、決定後の LINE 送付はモック動作
- 実データ（Places、営業、移動時間、LINE Messaging API / share）は未接続
- 認証・永続化・本番エージェントは未実装

次の実装境界（この ADR の範囲内）:

1. 現在地 + 営業中 + 徒歩時間で3件を返す
2. 決めた店を LINE で共有する（マップリンク）
3. 検索履歴と条件・保存の永続化

次の実装境界（この ADR の外。NVP 後）:

- LIFF / LINE 公式アカウントでの検索
- 二次会（人数）
- 予約・席確保
- 全国展開

## 8. 未決（意図的に開けている）

- 正式なプロダクト名（ima. は仮）
- 課金（最初は無料で「歩いた」を取る）
- LINE ログインの可否（最初は必須にしない）
- 写真・店舗データの供給元とライセンス
- 二人で同じセッションを見る方法（当面は1台 + LINE 送付）
