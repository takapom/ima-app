# ADR 0007: LLM主導の探索と能力に基づくTool設計

- **Status:** Accepted
- **Superseded in part by:** [0008](./0008-initial-tool-catalog.md)（初期Toolの選定方針。以下の非限定方針は当時の記録。LLM主導の責務分担は維持）
- **Date:** 2026-09-08
- **Deciders:** プロダクトオーナー（本議論）
- **関連:** [0003](./0003-plugins-and-dialogue.md)、[0006](./0006-lightweight-frontend-hexagonal-backend.md)。両者を維持し、実行主体とTool選定方針を明確化する。

## Decision

LLMがユーザーのプロンプトを受け取り、意図を理解し、必要なToolと引数を選び、観測結果を組み合わせて回答する。ApplicationはLLMの責務外の実行基盤と状態管理を補う。

- LLM: 意図理解、探索方針、Tool選択、追加調査、比較、回答の構成。
- Application / Harness: 原文・履歴・必要な文脈の提供、Tool呼び出しの型・権限検証、実行、期限・キャンセル、結果・エラーの返却、状態保存、出力契約の検証。
- Tool / Adapter: 能力の契約に沿った情報取得や計算。アプリの状態や提案方針を所有しない。

Applicationが発話を先回りして解釈し、固定の検索手順・追加調査・ランキングを自動適用する構成は採用しない。営業・徒歩・終電の計算は決定的な処理としてToolから提供できるが、利用する行動はLLMが選ぶ。

出力契約の検証と探索手順の強制は分ける。契約違反はLLMへ検証エラーとして返し、Applicationが勝手に候補や回答を書き直さない。既存の事実検証方針を撤廃する決定ではない。具体的な必須根拠・検証条件・制限到達時の動作は別途整合させる。

## Toolの選定方針

**「初期はToolを最小限にする」を選定基準にしない。** LLMがプロダクトのジョブを遂行するために必要な能力を洗い出し、その能力に基づいて公開面と契約を設計する。

以前に提案した `search_places` / `get_place_details` / `submit_cards` の3操作への限定は採用しない。この決定は個々の操作名を禁止するものではなく、その3つだけで十分とする判断を撤回するもの。

Tool数の少なさ自体を目標にせず、各能力の目的、入力、観測結果、利用場面、差し替え可能性を説明できることを重視する。具体的なToolカタログはまだ未決。

`submit_cards`は引き続きApplicationの終端操作。モデル向けの呼び出し面を持つことと、外部サービスのAdapterであることは区別する。

## 次の作業

ユーザーの利用場面から必要な能力を洗い出し、Tool候補ごとに「いつ使うか・何を受け取るか・何を返すか・どのPortへ接続するか」を定義する。最初から個数上限や3操作への集約を前提にしない。
