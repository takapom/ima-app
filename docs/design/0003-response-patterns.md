# 応答パターンと提示契約の検討

- **Status:** Proposal / 未採択
- **Date:** 2026-09-08
- **前提:** [ADR 0009](../adr/0009-contextual-response-presentation.md)。候補UIとメッセージを質問に応じてLLMが選ぶ。

- **具体化:** [自律応答ループ](./0004-autonomous-response-loop.md)で、この表を固定ルーティングではなく指針・評価ケースとして使う設計を記載。混合意図も単一パターンに限定しない。

## パターン案

| ユーザーの目的 | 入力例 | 提示案 | 情報取得の判断 | 既存候補の扱い案 |
|---|---|---|---|---|
| 新しく探す | 食後に甘いもの食べたい | 候補UI + 短い紹介 | 必要な候補を検索 | 新しい候補セット |
| 条件を変える | もっと近くがいい | 候補UI + 変更点 | 既存の根拠で足りなければ再調査 | 必要な候補を更新 |
| 理由を知る | なんでここがおすすめ？ | メッセージ | 既存の根拠があればTool不要 | 維持 |
| 比較する | この2つならどっち？ | 比較メッセージ。専用比較UIは未決 | 判断に必要な不足情報だけ調査 | 質問だけで勝手に入れ替えない |
| 特定店を確認する | ここ何時まで？ | 事実に基づくメッセージ。詳細UIは未決 | 鮮度・情報不足に応じて詳細取得 | 維持 |
| 決める・行動する | ここにする | 短いメッセージ + 既存の決定後操作 | 必要な場合だけ再確認 | 選択対象を維持。決定操作との接続は未決 |
| 不足・曖昧さを解消する | そっちじゃない／対象の店が曖昧 | 短い確認メッセージ | 文脈で解けるなら質問しない | 意図が不明なまま更新しない |
| 候補不足・障害 | 条件に合う店がない／API失敗 | 状況説明 + 可能な次の行動 | 再試行・部分結果は実行契約に従う | 有効な過去結果と今回の失敗を区別 |

この表はコードのif分岐や必須のTool呼び出し順を定めない。LLMが複数の目的を含む発話にも対応するための指針・評価例とする。

## 構造化出力の提案

メッセージとUIを別の内容要素として扱い、LLMはサポートされた表示要素を選ぶ。フロントはその契約を描画する。生HTMLや任意の実行コードは生成させない案とする。

初期はmessageと既存の候補UIの組み合わせで始め、比較・詳細などはメッセージで対応できるか検証する。専用UIの追加はこの文書で採択しない。

## 次に決めること

1. 初期にサポートする表示要素。messageと候補UIで足りるか。
2. メッセージのみ、候補UI + メッセージそれぞれの最終応答スキーマ。
3. submit_cardsの検証結果を最終応答へどう接続するか。メッセージだけなら呼び出し不要とするか。
4. 既存候補を維持・更新・追加する指定方法と、メッセージの履歴表示。
5. 根拠のない断定をメッセージにも出さない契約。不明・期限切れの伝え方。
6. 確認質問が必要な状況と、最初の提案を不要に遅らせない指針。

各パターンについて「適切な答え方」と「避けたい振る舞い」を用意し、LLMの提示選択を評価する。
