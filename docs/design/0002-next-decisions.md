## 決定済み

ユーザーがアプリケーション設計と初期Tool最小構成を明示的に確定した。以下を実装の前提とする。

| 対象 | 決定 | 正となるADR |
|---|---|---|
| 配置 | 1リポジトリ、iPhoneとWorker + DOの2デプロイ面 | [0006](../adr/0006-lightweight-frontend-hexagonal-backend.md) |
| フロント | UI + hooks/state + services。Port・DI・Repositoryクラスを一律に導入しない | 0006 |
| バックエンド | ヘキサゴナル。CoreがPortを所有し、外部技術をAdapterへ分離 | 0006 |
| 探索の主体 | LLMが原文・履歴を受け取り、Toolと引数、追加調査、比較、回答を選ぶ | [0007](../adr/0007-llm-led-tool-orchestration.md) |
| Application | 文脈提供、型・権限検証、実行、期限・キャンセル、状態保存、出力契約の検証を補う。固定探索や自動ランキングを先回りして適用しない | 0007 |
| 初期操作 | search_places / get_place_details / submit_cards の3つ | [0008](../adr/0008-initial-tool-catalog.md) |
| Toolの境界 | 必要な入力と実行文脈を受け、結果を返す。アプリ状態・提案方針を所有しない | 0006・0008 |
| 提案確定 | submit_cardsはApplicationの終端操作。検証エラーはLLMへ返し、勝手に回答を書き換えない | 0007・0008 |

| 操作 | 用途 |
|---|---|
| `search_places` | 気分・目的に合う候補を探す |
| `get_place_details` | 特定候補の不足情報を調べる。供給可能な項目だけ |
| `submit_cards` | 主提案と別案を選び、確定を要求する |

3操作は固定実行順ではない。追加調査が必要かもLLMが判断する。内部Port・Adapterの数はモデル向け操作数と一致する必要がない。

## 次の決定：3操作の能力範囲と入出力

**追記:** [ADR 0009](../adr/0009-contextual-response-presentation.md)で、メッセージ併用と質問に応じた提示を採択。[応答パターン案](./0003-response-patterns.md)を先に整理し、最終応答スキーマとsubmit_cardsの契約を合わせて設計する。候補UIを毎ターン必須とはしない。

**最初の作業は、検索で返す情報と詳細取得で補う情報を、項目単位で分けること。** その後、モデル指定値とHarness注入値を分け、valibotスキーマへ落とす。

| 操作 | 決めること |
|---|---|
| search_places | 検索語・気分・エリア等の入力、位置の扱い、件数、候補ID、検索時点で返す事実 |
| get_place_details | 指定ID・要求項目、一括取得可否、営業・徒歩・終電・予算等の対応範囲、未対応と不明の区別 |
| submit_cards | 主提案・別案・理由・比較文、根拠の参照方法、0〜2件しかない場合、拒否理由と修正方法 |

取得可能な情報と、提案に必須とする根拠は合わせて設計する。営業・徒歩・終電の情報を取得できないのに必須検証だけを置かない。実際の供給能力はAdapter実装前に公式仕様で確認する。

## 既存Draftとの整合

旧[詳細設計](./0001-iphone-next-spot.md)は履歴として残っている。現在のADRに反する記述を新実装の前提にしない。

決定済み方針で読み替える事項:

- 技術レイヤの一律の上→下依存は、フロント簡素化・バックエンドの依存逆転へ変更。
- カタログを渡さない記述、Tool内だけでLLMを呼ぶ記述は、LLM主導のループへ変更。
- 3操作への限定を採用しない0007の旧選定方針は0008が上書き。
- 営業・徒歩・終電等を独立したモデル向けToolとして必ず公開する前提は置かない。
- スクリプトモードへの自動切替は確定事項にしない。モデル障害時の動作として別途決める。

詳細契約とともに解消する事項:

- Resultとthrowの使い分け。
- 前ターンの観測保持と、今回runの取得結果だけを許すsubmit条件。
- ターンごとのdeleteAllに見える記述と、スレッド存続中の保持。
- Agentのphaseと共有スキーマの不一致。
- 旧案のモデル4回・8秒が新Tool契約で成立するか。ユーザーの会話回数とは区別する。
