# 変更の差分と方針を説明する（HTML版）

対象範囲の仕組みを構造図とコードベースの解説で示したうえで、他のエンジニアやビジネス側が「なぜ変えるのか」「何がどう変わるのか」「どのような影響があるのか」を共有できる日本語の説明資料を作る。クイズや理解度テストは含めない。

## 調査すること

- 比較元と比較先を特定する。コミットID、比較範囲、未コミット変更の範囲など、どの差分を説明したかを資料に明記する。対象は依頼や会話の文脈から判断し、特定できない場合だけ確認する。
- 対象範囲の入口から処理、状態の保存、外部連携、結果の返却まで、実際のコードをたどる。差分に含まれない関連コード、呼び出し元、テスト、現行仕様も読み、対象範囲が一連の処理としてどう動くかを把握する。調査をリポジトリ全体へ無制限に広げない。
- 冒頭で説明する構造と動作が、どの時点のコードに基づくかを明記する。原則として比較元（変更前）の仕組みを説明し、その後に変更を重ねる。新規機能の場合は接続先となる既存の仕組みを説明し、新設する部分と区別する。
- 方針や変更理由は、ユーザーの説明、現行仕様、関連するIssue・PRなどで根拠を確認する。過去の資料は判断の経緯を知るために使い、現行仕様と区別する。
- コードで確認できる事実、資料に記された判断、推測、提案を区別する。期待する効果を実測済みの成果として扱わず、理由が確認できなければ未確認と明記する。

## 説明の組み立て

本文は必ず「対象範囲の全体像と構造図」「コードベースに沿った動作説明」から始め、その後に変更を説明する。説明の深さは変更の規模と読者に合わせる。該当しない影響や対応を埋めるために内容を作らない。

1. **対象範囲の全体像と構造図**：その機能が誰のために何をするのか、どこからどこまでを扱うのかを短く説明し、構造図を提示する。入口、主要な構成要素、責務の境界、保存先や外部サービスを必要な範囲で示す。矢印には呼び出しや受け渡すデータの意味を付け、対象外の要素は外部との接点として示す。
2. **コードベースに沿った動作説明**：構造図の要素と、実際のファイル・主要な関数やクラス・責務を対応付ける。代表的な操作や入力を1つ使い、どこから呼ばれ、どの処理や状態変化を経て、何が返るのかを実行順に説明する。重要な分岐や失敗時の動作も対象範囲に応じて補足する。コード参照と必要最小限の抜粋を付け、ディレクトリ一覧だけで終わらせない。

3. **変更の要点**：何を、なぜ変更するのか、誰にどのような影響があるのかを短く述べる。ビジネス側がこの部分だけでも方針を理解できるようにする。
4. **変更前と変更後**：同じ操作・入力・利用場面を使い、以前の挙動と変更後の挙動を対比する。「変更前／変更後／利用者や業務にとっての意味」の表や具体例を使う。内部実装だけの変更なら、その範囲と外から見える挙動への影響を説明する。
5. **方針と判断理由**：解決する課題、採用した方針、その理由と制約をつなげて説明する。代替案やトレードオフは、判断を理解するうえで必要なものを扱い、実際に検討された案と説明のための仮定を区別する。決定済みの内容と未決の内容を明確にする。
6. **影響と留意点**：ユーザー体験、業務フロー、運用、互換性、費用など、変更に関係する影響を説明する。期待する利点だけでなく、制約や必要な対応も示す。数値や効果には根拠を付ける。
7. **実装の根拠と検証状況**：冒頭の構造図と動作説明に対応させ、どの構成要素や処理経路を変更したかを示す。エンジニアが確認できるよう、責務・データの流れ・入出力・重要な失敗時の挙動がどう変わるかを説明する。関連するコード・テスト・仕様への参照を付け、実行済みの検査と未検証の点を区別する。
8. **次に必要な対応**：移行、周知、追加検証、未決事項の判断など、必要なものがある場合だけ、対象者と対応内容を示す。担当者や期限が未定なら推測で埋めない。

## 読者への伝え方

- 冒頭の構造図は業務や利用者の言葉で役割を示し、続くコードベースの解説で実装名と結び付ける。専門用語は初出時に短く説明する。詳細なコード抜粋などの補足は後半や折りたたみに置けるが、対象範囲の基本動作の説明は冒頭に残す。読者が指定されている場合は、その人の判断に必要な情報を優先する。
- ファイルの列挙や差分の貼り付けだけで終わらせず、「この変更によって、どの挙動や責務が変わるか」を説明する。コード例は根拠として必要な範囲に絞る。
- 冒頭の構造図は必須とする。追加の図解は、変更前後の画面・業務フロー・データの流れが伝わりやすくなる場合に使う。図には説明を添え、データの流れには具体例を入れる。構造図の要素と接続は、確認したコードに基づかせる。
- 別の人に共有しても意味が通じるよう、会話の省略表現を避け、対象と前提を明記する。参照先はリポジトリURLとコミットに対応するパス・行番号などを使い、ローカルパスしか分からない場合は存在しないURLを作らない。

## HTMLの出力

- CSSを含む、単体で完結するHTMLファイルを1つ作る。JavaScriptは表示の切り替えなどに必要な場合だけ含め、外部アセットに依存させない。
- 見出しと目次を備えた、縦に続く1ページにする。最上位の構成にタブを使わず、スマートフォンでも読みやすくする。補足の技術詳細は折りたたみにしてもよい。
- 図はHTMLとCSSで構成し、ASCII文字による図は使わない。コードブロックは`<pre><code>`を使い、`pre`に`white-space: pre`または`pre-wrap`を指定する。コードや差分を埋め込む際はHTMLとしてエスケープする。
- 保存先と命名は次節に従い、ケースごとのフォルダに`index.html`を格納する。
- 保存後、冒頭に構造図とコードベースの動作説明があること、図とコード参照の対応、比較範囲、説明と根拠の対応、コードの改行、ページ内リンクを確認する。ブラウザーで表示を確認できた場合は、その結果も伝える。
- 最後に生成したファイルへのリンクと、調べた範囲・残る未確認事項を簡潔に返す。説明資料の作成を、対象コードの修正へ広げない。

## 保存先と命名

- ユーザーが指定した保存先を優先する。指定がなければ、対象リポジトリ内の`docs/code-explanations/`を保存先のルートにする。`/tmp`は一時生成・検査に使い、完成資料の保存先にはしない。
- 1ケースを「説明対象・目的・基準コミットまたは比較範囲が一まとまりの資料」とし、ルート直下に`<subject>-<aspect>/`を作る。フォルダ名には説明対象と説明内容だけを表し、年月日は付けない。
- `<subject>`は対象機能・仕組み、`<aspect>`は何を説明するかを示す。「AIの構造」なら`ai-architecture`、「会話履歴の保持」なら`conversation-history-retention`、「検索Providerの差し替え」なら`search-provider-swap`とする。対象と説明内容を合わせて2〜5語程度を目安に、コードや仕様で使う用語を英小文字・数字・ハイフンで表す。
- フォルダ名だけで「何について、何を説明する資料か」が分かることを確認する。`ai`のように対象だけの名前、`case1`、`misc`、`latest`、`report`など内容が分からない名前は避ける。リポジトリごとの保存先なので、プロジェクト名の階層は追加しない。
- HTMLのファイル名は`index.html`に統一する。主題は親フォルダで表し、ファイル名へ重複させない。本文には対象範囲と基準コミット・比較範囲を明記する。
- 同じケースの修正は既存の`index.html`へ反映する。対象や比較範囲が変われば別フォルダを作る。同名の別ケースがある場合は対象や説明内容を具体化し、それでも重なる場合だけ末尾に`-02`、`-03`を付ける。別ケースの資料を上書きしない。
- ケースフォルダには完成資料を置き、生成スクリプト・一時ファイル・ローカルの進捗管理ファイルを混在させない。既存HTMLを移す場合は内容とリンクを確認し、元の共有URLへの影響を伝える。

例：

```text
docs/
└── code-explanations/
    ├── ai-architecture/
    │   └── index.html
    └── search-provider-swap/
        └── index.html
```

localhostでの閲覧を依頼された場合は、`docs/code-explanations/`を配信し、URLを`http://localhost:<port>/ai-architecture/`とする。応答にはHTMLの絶対パスへのリンクと、起動した場合だけlocalhostのURLを添える。
